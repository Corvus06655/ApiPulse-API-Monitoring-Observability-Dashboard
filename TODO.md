# ApiPulse Frontend Outcomes

- [x] **Responsive dashboard shell and visual system:** Build a premium developer-focused SaaS dashboard with dark graphite/charcoal background, electric lime `#B8FF64` and teal `#36DCC8` accents, subtle borders, restrained glow, clean typography, clear hierarchy, strong spacing, tasteful micro-interactions, professional charts/data tables, and responsive mobile layout. Include ApiPulse logo and responsive sidebar navigation for Overview, Monitored APIs, Check History, and Settings. Avoid generic templates, excessive gradients, clutter, and unnecessary animation.
- [x] **Real FastAPI integration:** Configure a centralized API client using `VITE_API_BASE_URL=http://127.0.0.1:8000` and provide `.env.example`. Use correct request paths/methods, JSON handling, HTTP errors, and refresh UI after create/update/delete/check. Adapt to actual backend schemas. The supplied source implements history as `POST /target/{target_id}/history` rather than the documented GET; the frontend tries GET then falls back to POST on HTTP 405. Its query also filters `CheckResult.id` rather than `CheckResult.target_id`; document the backend limitation/fix separately. Never use a fake API, fabricated uptime, hardcoded dashboard statistics, or treat target existence as healthy.
- [x] **Dashboard overview and monitoring data:** Show total monitored APIs, healthy APIs, down APIs, average response time, API status overview, response-time chart, recent check history, and prominent Add API action. Use actual stats and check history only; show unknown/no-check states when health cannot be determined. Use Recharts for meaningful visualizations; if there is insufficient actual time-series data, show an appropriate empty state instead of invented points. If the backend is unreachable, KPI cards display unavailable marks rather than false zeros.
- [x] **Target management and detail:** List monitored APIs; add a target using name and URL; view target details; edit targets; delete targets with a confirmation dialog; run a manual health check; show last known check status where available. Respect backend target fields `id`, `name`, `url`, and `created_at`, and check fields returned by the supplied checker.
- [x] **Statistics and history:** Display total checks, successful checks, failed checks, uptime percentage, and average response time. Display available history records with timestamp, HTTP status, response time, health status, and error details. Do not imply history completeness when the supplied backend query is wrong.
- [x] **Interaction quality, access, and operational states:** Implement loading skeletons, empty states, error messages, success feedback, responsive mobile layout, confirmation dialogs, accessible labels, and keyboard-friendly controls. All visible buttons and controls must perform their stated actions.
- [x] **Integration guidance and validation evidence:** Keep backend source intact. Document installation/run commands, frontend project structure, connecting to the existing FastAPI server, the minimal local CORS change, actual backend endpoint/schema discrepancies, and the backend-unavailable limitation. Install frontend dependencies, run the frontend build, fix compilation errors, verify endpoint paths/methods and UI loading/empty/error states, and report only checks actually run. Evidence: 8 API-client tests passed; Vite build passed; `GET /manus-routes.json` returned the declared `/` route; desktop/mobile previews showed backend-offline states; FastAPI port 8000 was unreachable in this Sandbox.
